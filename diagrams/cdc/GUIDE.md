# CDC 階層図・CDC 詳細図(非同期箇所の図)

RTL のどの階層に、どのクロックからどのクロックへの乗り換え(非同期箇所)があり、同期化されているかを見せる図。
RTL から作ったデータベース(`rtldb.py`)だけを元に描くので、同じ RTL なら誰が(AI が)やっても同じ図になる。

| 図 | 見せるもの | 作り方 |
|---|---|---|
| CDC 階層図 `cdc_hier.svg` | 階層(行)× クロックドメイン(列)の上に、乗り換えを線で | `cdcdiag.py hier`(`rtldb.py analyze` でも出る) |
| CDC 詳細図 | 乗り換え 1 本の回路(送り側の FF・途中の論理・同期化の段・取り込みの条件) | `cdcdiag.py detail` → `gatediag.py render` |
| ドメインの表 `cdc_map.svg` | ドメイン × ドメインの件数(全体の量) | `rtldb.py analyze` |
| 一覧 `cdc.md` | 全件・準静的の候補・階層の深さ・RDC | `rtldb.py analyze` |

## 手順
```
python3 scripts/rtldb.py build -f files.f --top TOP -I inc -o design.db
python3 scripts/rtldb.py analyze design.db -o out/ --png --async-in '外部入力の正規表現' --static '設定レジスタの正規表現'
python3 scripts/cdcdiag.py hier design.db -o out/ --png                         # 全体(浅い階層から)
python3 scripts/cdcdiag.py hier design.db -o out/ --png --focus u_pinmux --name cdc_hier_pinmux   # 1 ブロックに絞る
python3 scripts/cdcdiag.py detail design.db --dst 'u_ok\.q$' -o out/cdc_u_ok.yaml && python3 scripts/gatediag.py render out/cdc_u_ok.yaml -o out/ --png
python3 scripts/rtldb.py path design.db --src 'a_data' --dst 'u_ok\.q$'         # 階層をまたぐ経路を信号の並びで
```
1. まず全体の階層図を出す。行が足りずにたたまれたブロック(▸ 下位 n 段を含む)に要対策の線があれば、`--focus` でそのブロックの図を足す。
2. 要対策・要確認の線は、番号ごとに詳細図か `path` で回路を確かめる。
3. 動作中に変えない設定レジスタは `--static`、外から来る非同期の入力は `--async-in` で宣言して出し直す(宣言した理由を決定事項に残す)。

## CDC 階層図の決まり(R54)
配置は次の順で機械的に決める。手で動かさない。

**行(階層)**
- 行にするのは、乗り換えの端(送り側・受け側の FF)があるインスタンスと、その祖先だけ。
- 並びは階層パスの順(親の下に子、字下げ 16px、行の高さ 30px)。行の名前は上の行からの相対パス(generate の名前も入る)。右端にモジュール名と深さ。
- 子が 1 つだけで自分に端のない中間の階層は、子と 1 行にまとめる(`u_tx …(5 階層)… u_n`)。
- 同じモジュールの葉の兄弟が 4 つ以上あれば 1 行にまとめる(`u_wkup_detector_* ×19`)。
- 行が上限(`--rows`、既定 36)を超える時は、浅い階層から、同じ深さでは重い枝(要対策 → 要確認 → 件数)から行にし、入りきらない枝は親の行にたたむ(▸ 下位 n 段を含む)。
- `--focus` で絞った時、外にある端は一番下の「(この階層の外)」の行にまとめる。

**列(クロックドメイン)**
- 乗り換えに出てくるドメインだけ、FF の多い順に A, B, C…(10 列まで)。見出しに記号・クロックの源の名前・種類(primary / mux / generated / blackbox / async_in)・FF 数。列ごとに色を決め、色だけに頼らず記号を併記する。
- マス = その行(と、下の行に出していない下位)にある、その列のドメインの FF 数。乗り換えの端になっているマスは太枠で塗る。FF のない端(入力端子・データに使ったクロック)は破線のマス。

**線(乗り換え)**
- 同じ(送り側の行・受け側の行・送り側ドメイン・受け側ドメイン・重さ)は 1 本にまとめる。
- 送り側のマスの右端に ●、右の通路に出て縦に進み、受け側のマスの右端に ▶ で入る。通路は短い線から内側に割り当てる(1 本 19px)。
- 同じ行の中の乗り換えは、マスからマスへまっすぐ(左右の向きで上下にずらす)。
- 1 つのマスに複数の線が入る時は、相手の行の順に上下にずらす。

  | 重さ | 線 | 番号の丸 | 分類 |
  |---|---|---|---|
  | 要対策 | 赤・太い実線(2.6px) | 赤の塗り・白い数字 | 同期化なし / 同期化の前に論理 / 1 段目を使用 |
  | 要確認 | 橙・破線(1.8px) | 白地・橙の枠 | ゲートの形 / 多ビット同期 / 条件で取り込み / メモリ / 再収束 / クロックをデータに |
  | 同期化あり | 緑・細い実線(1.2px) | 白地・緑の枠 | 2 段以上 / グレイコード / エッジ検出 / 非同期 FIFO / ハンドシェイク |
- 線は重い順・件数の多い順に番号を振り、`--arcs`(既定 28)本まで描く。残りは一覧の最後に組数だけ書く。`--sev` で描く重さを絞れる。

**一覧(右)**
- 番号ごとに 2 行: 「[ドメインの記号] 送り側の行 → [記号] 受け側の行」と「重さ: 分類ごとの件数(受け側の FF 単位)・例の信号」。
- 見出しの件数は、受け側の FF 1 本を一番重い分類で 1 回だけ数える。

**凡例(下)**: 線の 3 種類、読み方(● から ▶ へ、マスの数字、太枠)、行のまとめ方、判定は構造だけを見たものであること。

## CDC 詳細図の決まり
ゲートレベル図(R52)の書式で、受け側の FF 1 本について次を置く。
- 左の囲み(青)= 送り側ドメイン: 送り側の FF(4 本まで)。右の囲み(紫)= 受け側ドメイン。
- 同期化あり: 送り側 → 同期化の段(実際の FF 名)→ 出力。エッジ検出は XOR を足す。
- 同期化の前に論理: 送り側の FF → 「組み合わせ論理」の箱 → 同期化の段。
- ハンドシェイク・非同期 FIFO: データの FF(メモリ)と、条件を運ぶ FF → 同期化 2 段 → 「条件の論理」(FIFO は「空でない(ポインタの比較)」)→ 「en の時だけ取り込む」→ 受け側の FF。
- ゲートの形: データと同期化した信号を AND の記号で合わせてから受け側の FF。
- 同期化なし: 送り側の FF(→ 論理)→ 受け側の FF。`gatediag.py` の lint が [CDC] を出す(判定の二重の確認になる)。

## 確かめ方
- `python3 scripts/rtldb.py selftest`: 答えのわかる RTL(`examples/rtl/cdc_cases.v` 21 通り + RDC、`cdc_deep.sv` 階層 9 段)で分類を確かめる。
  期待にない乗り換えが出ても失敗にする。新しい形の回路に対応したら、ここに答え付きで足す。
- 大きい RTL では、要対策を数本選んで `path` で経路を出し、ソースと突き合わせる。方式・実績・限界は `reference/rtldb.md`。

## 未決の時に聞くこと
- 外から来る非同期の入力端子はどれか(`--async-in`)。
- 動作中に変えない設定レジスタ・OTP の値はどれか(`--static`)。理由も残す。
- 分周クロック・切替クロックを元と同期とみなしてよいか(既定: 分周は同期、切替は別ドメイン)。
